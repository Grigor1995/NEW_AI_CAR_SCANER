# Database design

SQLite version 1 migration is an atomic transaction in Store construction; repeated opens preserve rows. Tables: accounts(id,email UNIQUE,salt,password,active); roles(account FK,role constrained to USER/CUSTOMER/ADMIN/MARKET, composite PK); tokens(hash PK,account FK,expires); vehicles(id PK,owner FK,payload JSON); settings(account PK/FK,payload JSON); audit(id,actor,action,subject,at). Vehicle owner lookup is indexed. SQL uses bound parameters and foreign keys. Only password derivations and token hashes are persisted; login responses contain the short-lived bearer only once.

App and standalone backend SQLite databases are separate unless explicitly configured to use the same controlled path; no sync exists. Files are owner-readable/writable. Directory ACLs and SQLite journal permissions require deployment review. Backups must be made with SQLite backup tooling while live; schema rollback/data deletion tooling is not implemented. Future PostgreSQL schemas should be separate domain-owned migrations with explicit owner/consent constraints, outbox and retention policies. Live PostgreSQL and recovery tests are BLOCKED / NOT RUN, not satisfied by SQLite.
